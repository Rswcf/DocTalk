## Findings

1. **[BLOCK] Collection creation still acquires `users` before an existing `documents` parent, so the stated global order is incomplete and the deletion resolver can hang.**
   - **Location:** `backend/app/api/collections.py:142-148` and `backend/app/api/collections.py:157-163`, against `backend/app/services/doc_service.py:162-178`, `backend/app/services/predebited_job_service.py:125-132`, `backend/app/services/extraction_service.py:778-826`, and `backend/app/services/domain_mode_access.py:182-200`.
   - **Failing sequence:** Create a collection with an existing document in `body.document_ids`. The flush at `collections.py:148` inserts `Collection(user_id=...)`; its user FK takes and retains `FOR KEY SHARE` on that existing `users` row. In parallel, delete that document after it has a queued/running unreconciled extraction job. Delete locks the document `FOR UPDATE` at `doc_service.py:162-166` and awaits the fresh-session settlement resolver at `predebited_job_service.py:125-132`. Collection creation reaches the junction INSERT at `collections.py:159-163`, whose document FK now waits for delete's parent lock while the collection transaction continues to hold the user key-share lock. The resolver refunds at `extraction_service.py:778-783`, locks/fails the job, and then `release_failed_extraction_trial_sync()` requests `FOR UPDATE` on the same user at `domain_mode_access.py:189-190`; that conflicts with the collection transaction's key-share lock. The wait graph is collection `users -> documents`, outer delete `documents -> awaited resolver`, resolver `-> users`. PostgreSQL cannot detect the Python `await asyncio.to_thread(...)` edge, so both otherwise-valid user operations can remain hung and the predebit cannot settle while the cycle persists. This is the same rejecting-work class as round 2's blocker, reached through a collection path the new global-order claim did not cover.
   - **Suggested fix:** In `create_collection`, parse/deduplicate the requested document IDs and lock all owned existing document rows in stable UUID order with `FOR KEY SHARE` **before** flushing the new `Collection` row. Then create the collection and junction rows. This preserves compatibility with reparse's `FOR NO KEY UPDATE`, makes collection creation wait before it owns any user-row lock when deletion won, and leaves the adjudicated delete side unchanged. Add a real-Postgres regression that pauses document deletion in the extraction settlement resolver, concurrently creates a collection containing that document, and proves both requests terminate (delete wins -> collection must omit/fail the vanished document; collection wins -> delete proceeds after its commit).
